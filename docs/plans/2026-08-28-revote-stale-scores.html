Implementation Plan · 2026-08-28

Re-voting: stale scores age back into the queue, and the bot asks again

Planning 0 / 0 tasks 0 / 0 steps TDD

Architecture

Today a voter who has scored every teammate on all six indicators is done forever: select_next_score_target excludes any (voter, player, indicator) that already has a scores row, so /vote returns 'nothing left to rate' and those opinions, formed when people barely knew each other, stay in the ratings indefinitely. This adds a rolling staleness window (REVOTE_AFTER_DAYS) so a score older than the window is re-offered after the unscored targets on other players, keeps the superseding UPSERT semantics while archiving the replaced value to a new score_history table, and adds a weekly DM job plus an admin /revote_ping so people are actually told they have work waiting. /revote_ping is a delivery trigger, not a reset: it chooses who gets a DM and never widens the staleness window, so nobody is ever asked to re-rate everything. The rating maths in rating.py is deliberately untouched, so team balance changes only because its inputs get fresher.

Response

Only the stale ones. /revote_ping is a delivery trigger, not a reset: it decides who gets a DM, never what they are asked. Plain /revote_ping DMs each reachable player who currently has pending targets, honouring the 7-day per-person nudge cooldown; /revote_ping force uses the same list but waives that cooldown so you can push twice in one week. Neither touches REVOTE_AFTER_DAYS or marks anything stale.

When the person then taps /vote, the queue serves what it always serves: teammates they have never rated first, then only scores older than REVOTE_AFTER_DAYS (60 days), oldest first. A score cast last week stays untouched however many times you ping.

So no path in this plan asks anyone to re-rate everything. That was the "admin-opened rounds" option you passed on in favour of rolling age. If you want it back it is small (a /revote_round that stamps scores.updated_at backwards past the window), but it is a different feature, and on a four-month-old database it would hand every player around a hundred prompts at once. Task 4.2 exists to size exactly that risk before the first automatic run.

The plan was vague on this, which is why the question came up: the architecture summary above and task 3.4 now state it outright, and 3.4 requires the same sentence in the module docstring.

Use AND (EXISTS (SELECT 1 FROM contacts c WHERE c.telegram_id = p.telegram_id) OR EXISTS (SELECT 1 FROM scores s WHERE s.voter_id = p.telegram_id)) — having cast any score is itself proof of an open DM, because the whole vote flow is DM-only.

Rationale

The cooldown is only recorded on a successful send (task 3.4), which is right for a transient failure but would loop forever on a permanently unreachable player. Filtering on `contacts` is what keeps that bounded.

Risks
  • Ghost players are `active=1` and `in_pool=1` by design so others can rate them. Forgetting the `is_ghost=0` filter means the job tries to DM a negative telegram_id every single week.
  • A player who blocks the bot after having DM'd it still has a `contacts` row, so they stay in the target list. That is a small, silent per-week failure the job logs; accept it rather than adding a failure-count column.
